The 70 / 30 split is by decision criticality, not lines of code. The decisions that require reasoning over messy multilingual input — what the user wants, which provider fits, when to book, what to say — are all LLM-driven. Code only handles lookups, filtering, persistence, and the safety nets that catch the rare bad LLM output.

1What each decision is driven by

Decision / capabilityDriverWhy
Parse messy multilingual request
"kal subah Gulshan mein plumber chahiye, paani leak ho raha hai"		 LLM Mixes Urdu, Roman Urdu, English, time references, urgency, location. No regex handles this.
Provider discovery (category + radius search) CODE Pure lookup — category filter + Haversine distance. Replaced the LLM here today; saved ~10s and removed a hallucination source.
Availability filter (does the provider work that day/hour?) CODE Calendar math. Was the LLM's job before; the LLM kept skipping it. Now deterministic guard runs after discovery.
Ranking — pick top 3 with reasoning
trade off distance vs rating vs price vs verified vs trust		 LLM This is the agentic core — explains why each choice, honors per-user preferences like "achha wala", "sasta", "female only".
Booking — try exact time, shift within window, propose alternatives LLM "Aap ne shaam kaha — 5 PM bhara tha, 6 PM book kar diya, same provider." That nuance is LLM judgment.
Booking ID validation / self-heal HYBRID LLM emits booking_id; code verifies it exists in storage; if not, code calls create_booking itself with the data we already have. User never sees the error.
Follow-up scheduling (reminders, post-booking nudge) LLM Decides reminder cadence based on category — same-day plumber differs from a wedding photographer 3 months out.
"Still there?" nudges when user goes idle mid-clarification LLM Reads the actual conversation transcript and writes a context-aware message in the user's gender + language. Replaces a stale hardcoded line.
Provider onboarding & profile editing — entirely via chat LLM No form. AI asks for name, service, area, hours, price, languages, gender, phone one at a time. Voice input + voice output match the customer chat exactly. In edit mode the user just says "price 3000 se 8000 kar do".
Bot voice (TTS) LLM Gemini speech-gen with prompt-driven style preamble; Cloud Chirp3-HD fallback. Voice gender (Aoede/Puck) matches the user's gender automatically.
Grammatical gender of bot speech (Urdu / Roman Urdu) LLM "kar rahi hoon" vs "kar raha hoon" — feminine for female users, masculine for male. Agent prompts have an explicit table.
Named-provider matching ("naam hai Saifullah") CODE Regex on cue words + catalogue lookup. Deterministic for reliability; agents would hallucinate non-existent names.
Booking lifecycle / polling / notifications CODE Mobile polls the booking endpoint every 4 s after request; on status change → chat message + local push notification.
Pipeline orchestration (which agent runs when) CODE TypeScript orchestrator in orchestrator.ts. Deterministic on purpose — agents handle decisions, code handles sequencing.

2Challenge requirements — what we hit and what we didn't

The seven core requirements

RequirementStatusEvidence
1. Understand user service requests in natural language DONE Intent agent handles Urdu (Nastaliq), Roman Urdu, English, and code-switched input. Voice input via STT in dictation mode. Multi-turn merging across clarification flows.
2. Identify relevant providers using location/context DONE Discovery: deterministic category + neighborhood + radius search (76 seed providers + new onboarded ones in Firestore). Open-domain Places API integration available behind USE_REAL_PLACES flag.
3. Select or recommend the best provider DONE Ranking agent surfaces top 3 with written reasoning; honors preferences (quality / price / speed / trust / female-only). User picks from a tile picker, or auto-book if only one match.

Provider-side

  • Conversational signup — POST /provider/chat (LLM, Gemini Flash-Lite) collects name, category, area, hours, price, gender, languages, phone one at a time. Voice in / voice out.
  • Conversational edit — same endpoint in mode:'edit'; pre-loaded with current profile, user just says what to change.
  • "Online / Off" toggle — POST /providers/:id/availability. Deterministic discovery filter drops providers with available_now:false.
  • Accept / decline / en_route / arrived / completed — provider taps a button → POST /providers/:pid/bookings/:bid/action. Customer's Bookings tab auto-refreshes every 8s.

Voice stack

  • STT: speech_to_text Flutter plugin in dictation mode (no auto-cutoff on pause).
  • TTS: Gemini speech-gen with style preamble ("speak naturally and warmly") → Cloud TTS Chirp3-HD Aoede / Puck fallback. Gender-aware voice (Aoede for female users, Puck for male). Audio cached in-session.

5Honest gaps

  • Follow-up reminder cron — agent writes scheduled_jobs to Firestore, no server-side worker fires them. AI-generated idle nudges work; time-based reminders don't.
  • API authentication — endpoints don't verify Firebase ID tokens. Demo-safe; production risk.
  • Discovery / ranking hallucination root cause — Gemini Flash-Lite sometimes skips its tool calls and fabricates JSON. Mitigated with: deterministic discovery (replaces the agent), name-hint regex, hallucination guards on booking_id with self-heal. Symptom contained but the underlying agent behavior wasn't fixed.
  • Profile photo handling — uploaded as base64 data URL in JSON body. Works but heavy. Should be Cloud Storage upload + URL.
  • Demo video & Antigravity-usage video — not recorded yet.

6Bottom line

All 7 core functional requirements are met end-to-end on a real Android phone — natural-language input across three languages, location-aware discovery, ranked recommendations with reasoning, simulated booking lifecycle, AI follow-up nudges, and a live trace panel showing every agent decision.

The system is ~70% agentic by decision-criticality — the parts a judge will care about (understanding intent, ranking with tradeoffs, conversational onboarding, smart booking) are all LLM-driven. The ~30% deterministic code is exactly where determinism helps: lookups, availability math, safety guards for the rare hallucinated output, and pipeline sequencing.

Anti-monolithic guarantee held: no if category == 'plumber' anywhere in the codebase. The taxonomy is a single JSON file that agents read at runtime. Adding a 33rd service category is one row.
