# Antigravity Artifacts

Every implementation plan, walkthrough, task list, task plan, and run trace generated by Google Antigravity during this project is saved here. This is **Submission Deliverable #6** and constitutes evidence for the 50% of the evaluation weighted on "Antigravity usage depth."

## Filename convention

```
YYYYMMDD-NN-{feature-name}-{kind}.md
```

- `YYYYMMDD` — date generated
- `NN` — sequence number that day (01, 02, …)
- `feature-name` — kebab-case, what was being built
- `kind` — one of: `plan`, `walkthrough`, `tasks`, `trace`

### Examples
```
20260517-01-orchestrator-agent-plan.md
20260517-02-orchestrator-agent-walkthrough.md
20260517-03-orchestrator-agent-tasks.md
20260518-01-intent-agent-plan.md
20260518-02-flutter-chat-screen-plan.md
20260518-03-flutter-chat-screen-walkthrough.md
```

## Capture process

For every Antigravity session:

1. **Before** the session: start OBS recording (`recordings/raw/`)
2. **During**: prompt Antigravity normally — let it generate plans / walkthroughs
3. **After**: copy each generated artifact into this folder with the naming convention above
4. Commit to git

Do not edit artifacts after capture. They are evidence — keep them as Antigravity produced them.

## What goes here vs. what doesn't

| Goes here | Doesn't |
|---|---|
| Implementation plans | Working source code (lives in `backend/` / `mobile/`) |
| Walkthroughs explaining what Antigravity did | Manual hand-edits or notes |
| Task lists & breakdowns | README / docs (live in `docs/`) |
| Trace / log exports from agent runs | Screen recordings (live in `recordings/`) |

## Why this matters

The hackathon brief says: *"submit artifacts like implementation plan, walkthrough, task list, task plan whenever you prompt it to use in development."* Reviewers will read these files to judge whether the work was genuinely produced in Antigravity. Sparse or retroactively-reconstructed artifacts = weak signal. Numerous, dated, sequential artifacts = strong signal.

**Aim: 15–30 artifacts by submission day.**
